# skill-improve 设计思路

本文件记录 skill-improve 为什么这样设计，以及接下来要做什么。运行时不加载，SKILL.md 也不引用它。

## 来源

宝玉《Warp 如何让 Agent 自我进化》（https://baoyu.io/blog/2026-08-28/warp-self-improving-agents），原文是 Claude 博客《How Warp builds self-improving agents on Claude》。核心做法：一个基础 skill 负责干活，一个改进 skill 定期收集人对产出的修改与评论，据此更新基础 skill。人只在原本工作的地方自然地改，收集与改进全由 Agent 完成。

## 关键决策（2026-10-12）

| 问题 | 决定 | 理由 |
|---|---|---|
| 改进是否要人审 | 不审，闸门通过就自动提交推送，回复里附一行撤销命令 | 逐次审核会让反馈不再低摩擦；做法与原型改动直接落库一致 |
| 冲突检查怎么做 | 本 agent 自己对照最近 3 份定稿，不起子 agent，不对照全部历史 | 子 agent 流程复杂且有成本；旧定稿可能只是当时的权宜写法，越旧越不可信。首轮实测的 6 处冲突全部来自最近两份定稿 |
| 一次性修改是否入 skill | 只出现一次的先不入，第二次出现才归纳 | 防止把某天随手的改法固化成规则 |
| 过时规则怎么清 | 现行规则被近期定稿明确推翻时，在冲突检查这一步删掉或改写 | 只追加不清理会产生沉积，skill 越写越长 |
| 草稿要不要同步 | 不同步，只从本机会话读（审核页、文档初稿快照） | 草稿只在改进那一刻有用 |
| 反馈来源 | 用户直接改出的定稿；主管等他人在用户产出上的评论（全部吸收）；聊天里的纠正原话 | 直接改是用户最自然的动作；评论来自他人 |
| skill 体量 | 改后字数不超过改前，确有全新裁决时最多净增 200 字 | 逼着合并旧规则，而不是继续往后堆 |
