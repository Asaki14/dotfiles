# Skill Improve

基础 skill 负责产出；本 skill 负责让它越用越准。用户改过的定稿就是**判例**：每一处修改都是一次裁决，本 skill 把裁决归纳成基础 skill 里的原则，让下一份草稿不再犯同样的错。用户只管自然地改，不审本 skill 的改动；把关靠下面的闸门，事后可一键撤销。

## 输入

调用方给出三样东西：

- **目标**：要改的 skill 目录（`~/.omp/agent/skills/<name>/`）和其中由反馈驱动的那一节（如 example-skill 的「写法」）。
- **新判例**：本次的草稿与定稿（用户直接改出来的结果），别人（如主管）在用户产出上的评论，或聊天里用户纠正的原话。草稿只需本机读得到（调用方会话里的审核页、文档初稿快照），不同步。纯确认（「好的」「收到」）不算。
- **近期判例**：该 skill 最近 3 份定稿（如 `~/reviews/*-final.md` 按日期取最新 3 份）。更早的定稿不做约束：写法一直在演进，旧定稿可能只是当时的权宜写法，越旧越不可信。

## 步骤

1. **逐处读差异**。对新判例的每一处修改写一行：改了什么（原文→定稿）。有草稿时逐句对比；只有定稿时，对照目标节逐条找定稿与现行规则不一致之处。完成标准：每处修改都有一行，没有「等若干处」。
2. **区分事实更正与写法裁决**。只针对当天内容的更正（补了一个人名、改了一个日期）不进 skill；能推广到以后草稿的才是裁决（措辞层级、该留该删、标题写法、状态词）。拿不准时看近期判例里有没有同类修改：出现过两次以上即算裁决；只出现一次的先不进 skill，它还会留在下次调用的近期判例里再比一次。
3. **归纳成原则**。每条裁决写成「做什么 + 为什么」，为什么写读者或用途，不写日期和来源轮次。优先并进目标节里最近的一条原则、改写那条，而不是新增一条；示例只留一对最典型的「原文→定稿」，放进原则句内。用户原话引用（「」括起、写明是原话的）照抄保留。
4. **过闸门**（全部通过才提交）：
   - **近期一致**：本 agent 自己把改后的目标节逐条对照近期判例，找「按新规则写会被改掉的定稿原文」，不起子 agent。有冲突就收窄适用范围，不整条删。反过来，现行规则被近期判例明确推翻的，删掉或改写：过时规则只从这里清出去。
   - **不丢规则**：改前目标节的每条规则，改后要么仍在，要么在提交说明里写明去向（并入哪条、被哪份定稿推翻）。用户原话引用一条不少。
   - **不增肥**：`wc -m` 量目标 SKILL.md，改后字数不超过改前；确有全新裁决时最多净增 200 字。超了先合并相近原则。
5. **提交**。在 `~/.omp` 仓库只 `git add` 目标 skill 的文件，提交信息 `skill-improve(<skill>): <一句改了什么>`，正文列判例来源（文件名）和第 4 步的规则去向，然后 `git push`。闸门未过时不提交，在回复里说明卡在哪道闸；这批判例下次调用时随新判例一起重跑。
6. **告知**。在调用方本轮回复末尾加一行：`skill 已更新：<改了什么>；撤销：git -C ~/.omp revert <hash> && git -C ~/.omp push`。

完成标准：新判例的每处修改都已归类（事实更正 / 写法裁决）；每条裁决已进入目标节或因闸门未过写明卡点；提交已推送或未提交原因已告知。

## 原则

- 写原则不写死规则：「状态词只写本人推进到哪一步」胜过枚举十个禁用词。枚举只留作原则句里的例子。
- 讲为什么：理由让下一次遇到没见过的情况也能推出对的写法。
- 目标节只放现行规则。日期、轮次、「首次定稿 6/6 条」这类过程记录写进提交说明，不写进 skill。
