# Project Scaffold

为 Agent 主导维护的 PM 项目建立可预测骨架。Leading word：**YAGNI**——只为当前真实边界建立层级和索引。

## 硬约束

- 根目录 `README.md` 是项目唯一 README；Agent 规则以根目录 `CLAUDE.md` 为唯一来源。
- `ROADMAP.md` 维护任务状态；`CHANGELOG.md` 记录已完成的重大决策、迁移和里程碑。
- `sources/INDEX.md` 与 `outputs/INDEX.md` 固定作为全局总览；其他目录以当前不可替代的导航价值决定是否使用 `INDEX.md`。
- 正式交付使用稳定的语义化路径：单文件由文件名表达产物类型，形成独立交付边界后才建立目录。
- 已有项目在用户确认最终架构与逐文件迁移映射前保持文件不变。
- 保留既有 Git 成果；由用户决定提交、推送和 commit 改写。

## 按需参考

- 审计、设计或迁移目录时，完整读取 [`STRUCTURE.md`](STRUCTURE.md)。
- 创建或修改治理文件时，读取 [`GOVERNANCE.md`](GOVERNANCE.md) 中对应文件章节；裁定权威信息分工时先读其“职责分工”。
- 处理需求 brief、报告、正式交付生命周期、Phase 或迁移映射时，读取 [`DELIVERABLES.md`](DELIVERABLES.md) 中对应章节。
- 设计方案和最终验收均完整读取 [`VALIDATION.md`](VALIDATION.md)。

## 分支

- **新项目**：定界 → 设计 → 创建 → 验证。
- **已有项目**：定界 → 审计 → 方案访谈 → 迁移 → 验证。

## 1. 定界

确认项目定位与决策对象；提出方、执行人和审核方；目标、非目标、交付物与验收标准；根目录与当前材料；是否存在正式报告或复杂需求 brief。会改变目录或迁移范围的未知项使用 `questionnaire`，一次裁定一个关键问题。

**完成条件**：每个字段已有答案，或有证据表明该未知项不影响当前架构。

## 2. 审计已有项目

新项目跳过。完整读取 `STRUCTURE.md`，并按内容读取 `DELIVERABLES.md`：

1. 区分 Git upstream、本地未推送 commit、未提交工作区与迁移前回滚基线；
2. 盘点全部目录、文件、软链、忽略规则和跟踪状态，按结构边界判断保留或收敛；
3. 检查治理职责、正式交付生命周期、Phase、报告规范、证据可追溯要求和历史兼容入口；
4. 搜索 Markdown 链接与锚点、HTML 本地引用、脚本默认路径、文档命令和构建入口；
5. 标记缓存、临时文件、重复副本和过期材料。

**完成条件**：每个现有文件和目录均归入“保留、迁移、合并、删除、待裁定”之一；每个待裁定项均说明对目标架构的影响。

## 3. 设计并确认

读取所需参考。已有项目提供 2–3 个可执行方案；新项目只给满足当前需求的最小方案。每个方案包含目标目录树、模块职责、权威信息分工、正式交付形态、验证矩阵，以及每个子目录和局部 `INDEX.md` 的当前保留理由。

已有项目还需逐文件展开原路径 → 新路径，明确移动、改名、合并、拆分、删除、正式交付生命周期、引用与工具更新范围，以及四类 Git 状态。用决策访谈裁定所有会改变迁移结果的问题。

**完成条件**：每个迁移对象、删除项、权威来源和兼容策略均有唯一结果，并获得用户确认。

## 4. 实施脚手架

按确认方案落地文件分类、目录收敛、治理文件和正式交付生命周期；同步更新全部链接、锚点、HTML 引用、索引、软链、脚本路径、文档命令和报告规范。重大架构决策写入 `CHANGELOG.md`，迁移映射逐文件写入 `outputs/INDEX.md`。

**完成条件**：确认方案中的每个迁移对象和引用更新均已落地；映射无遗漏；旧路径仅存在于明确迁移历史；既有 Git 成果均可定位。

## 5. 验证并交付

完整读取 `VALIDATION.md`。逐项判定适用性，为每个适用项保留命令输出或文件证据；修复失败项，或给出具体阻塞和所需外部动作。展示最终目录树、迁移映射、验证结果、保留风险、skill 变更摘要，以及四类 Git 状态。

**完成条件**：验证矩阵每一项均有“通过”证据或“不适用”理由；所有失败项已修复，或已证明需要用户或外部动作。
